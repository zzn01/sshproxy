# Desktop app

A desktop app, so people who never open a terminal can use sshproxy:
double-click, add an SSH server, switch the system proxy on.

## Approaches

- **Wails v3 window + tray around the web control panel (chosen).** The
  control panel is a web page served by sshproxy; Wails shows it in a
  native window (WKWebView / WebView2 / WebKitGTK) and provides the tray /
  menu bar icon. Wails v3.1 has experimental CGO-free (purego) backends for
  macOS and Linux, and Windows never needed cgo, so every desktop build is
  made from one machine with `CGO_ENABLED=0`. The same panel also works in
  a browser (`sshproxy -gui`), e.g. on headless Linux.
- **Tray (fyne systray) + panel in the default browser.** First version
  built; it looks like a web page rather than an app, and the macOS tray
  needed cgo anyway. Replaced.
- **Browser app mode (`--app=`), purego webview wrappers (Glaze,
  opentoys/webview), pure-Go drawn toolkits (gogpu/ui, Proton, MyGo).**
  Depend on an installed Chrome/Edge, have no tray, or need the UI rewritten
  in an early-stage toolkit. Rejected.
- **Electron / Tauri shell.** Extra toolchain and much larger downloads.
  Rejected.

No code signing is available: macOS users must allow the app once in
System Settings → Privacy & Security; Windows shows SmartScreen once. The
README explains both.

## Behavior

- Desktop builds start the app when run without a destination: engine
  from the default config file (created on first change), a tray / menu
  bar icon, and the control panel window, shown on first run and whenever
  an SSH login needs a password. Closing the window keeps sshproxy running
  in the tray. `sshproxy -gui` in a command line build does the same with
  the panel in the browser and no tray.
- One instance: launching the desktop app while it runs shows the running
  one's window and exits (Wails single instance), checked before the proxy
  port is taken. On desktops without a tray (plain GNOME) this is how a
  closed window comes back, and the panel says so when no tray host
  (`org.kde.StatusNotifierWatcher`) is on the session bus, or when it runs
  in the browser as a fallback. Without a window (browser panel, `-gui`) the
  running one saves its panel link to `<cache dir>/sshproxy/panel-url`
  (0600, removed on exit); a new launch that finds a panel answering there
  with its token opens it in the browser and exits. A busy port can't be
  the signal: the default listen address moves on to the next free port.
- Tray menu: Open sshproxy, System proxy on/off, Start at login on/off
  (checkboxes), Quit. Both switches are also at the top of the panel.
- Start at login uses Wails' autostart manager: SMAppService login item
  for the bundled macOS app (LaunchAgent otherwise), the HKCU Run key on
  Windows, an XDG autostart entry on Linux.
- The system proxy choice is remembered in the config (`system_proxy:
  true`) and applied whenever the app starts, so starting at login brings
  the proxy back. Quitting still turns the OS setting off without
  forgetting the choice.
- Control panel (served on the proxy port under `/ui/`):
  - Status: proxy address, system proxy switch, last error.
  - Servers: added with the SSH form, which checks the login before
    saving; the name comes from the host. List shows health and latency;
    groups expand to their members and current choice.
  - Servers: rename (rules, chains and pins follow), SSH key file and jump
    host, remove. Clicking a node pins it.
  - Routing: structured rows (Domain / IP range, value, destination picked
    from a list of servers, chains, "Fastest of all" and "Direct"), reorder,
    remove, inline validation (the match type follows what is typed), and
    an "Everything else" destination. Saved as ordinary rule lines with a
    final `<destination> *`.
  - Backup chains (config `groups`): create, delete, rename, choose "first
    that works" or "fastest", add / remove / reorder members, pin a member.
  - Password / passphrase prompts for SSH appear as a dialog in the panel.
  - The SSH form lists the concrete hosts of `~/.ssh/config` (wildcard and
    negated patterns left out; hosts from `Include` files not listed) with
    what each resolves to, and shows live what the typed server resolves
    to. Empty port and user fields are left to the config.
- Changes are written to the config file and the engine reloads in
  place: the listener stays, new connections use the new setup.
- `fastest` is a built-in group of every server (lowest latency first),
  reserved like `direct`. With no rules all traffic goes to it, so several
  servers without rules are fine.
- Pins (config `pins: {group: member}`) make a group use
  that member while it is healthy and fall back to automatic choice when
  it fails. Pinning applies to the running setup without a reload.
- System proxy: macOS via `networksetup` (web, secure web and SOCKS proxy
  on every enabled network service); Windows via the Internet Settings
  registry keys plus a WinINet refresh; Linux via GNOME `gsettings` and
  KDE Plasma 5/6 `kioslaverc` (kwriteconfig, then a KIO reload signal over
  D-Bus); both are set when available, so any GNOME- or KDE-based desktop
  works. Other Linux desktops have no system proxy setting: turning it on
  there reports that the proxy must be set by hand. It is
  turned off on quit, and at startup a leftover setting pointing at our
  address (e.g. after a crash) is cleared.
- When switching the system proxy on fails (from the switch, the tray or
  the remembered setting at startup), the panel shows why, next to the
  server and port to enter by hand and where that setting lives on the
  current OS. "Set up by hand" opens the same help at any time.
- Test (`POST /api/check`) sends a request to the health-check URL through
  sshproxy's own port, like any app would, and reports whether the OS
  proxy settings point at it. The page then fetches
  `http://check.sshproxy.invalid/`, a name that never resolves and that
  sshproxy itself answers (with CORS allowed), so success proves the
  page's own traffic — and with it the system proxy — goes through
  sshproxy. This also covers proxies set by hand on desktops we can't read.

## Security

- The panel and its API are only served to requests whose Host is a
  loopback address, and the API requires a per-run random token sent in an
  `X-Token` header (the panel gets it from the URL the tray opens), so web
  pages in the browser can't drive it.

## Builder's calls

- UI text is English, per the project rule for source strings.
- Release adds desktop builds (`-tags gui,production,purego`,
  `CGO_ENABLED=0`): an ad-hoc signed macOS `.app` per architecture (menu bar
  only, `LSUIElement`), a Windows GUI exe (`-H windowsgui`) and Linux
  binaries (need GTK4/WebKitGTK 6.0 at runtime; without them, or without
  a display, the panel opens in the browser as with `-gui`). CLI builds
  stay.
- If the experimental purego backend misbehaves on a platform, that
  platform's desktop build falls back to cgo (macOS builds natively here).
- The window loads the panel through Wails' in-process asset handler, so
  no network request leaves the app; the token still guards the API.
- The config file is rewritten as YAML by the panel, so comments in a
  hand-written config are lost once it is edited from the panel.
