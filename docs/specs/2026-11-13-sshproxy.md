# sshproxy: HTTP/HTTPS proxy over SSH

> The first version. Since then sshproxy also reads a config file with
> several servers, groups and failover (see the README), supports
> `ProxyCommand`, and has a [desktop app](2026-11-13-desktop.md) that sets
> the system proxy. Non-goals below that say otherwise are out of date.

## Intent

Anyone who can log into a server over SSH should be able to turn it into a
local HTTP/HTTPS proxy with one command and zero setup, on either end.

Target users include people who do not know SSH: they were handed a host,
a username and a password (sometimes a key file) and have no `~/.ssh/config`,
and on Windows possibly no `ssh` binary. "The more foolproof the better" is
the guiding requirement.

```
$ sshproxy root@1.2.3.4
Password for root@1.2.3.4: ******
Connected to 1.2.3.4
  Proxy:  http://127.0.0.1:7890  (HTTP, HTTPS and SOCKS5 on the same port)
  Shell:  export http_proxy=http://127.0.0.1:7890 https_proxy=http://127.0.0.1:7890
  Reconnects automatically. Press Ctrl+C to quit.
```

## Goals

- Single static binary, no runtime dependency (no system `ssh`, nothing on the
  remote beyond a stock sshd with TCP forwarding allowed, which is the default).
- `sshproxy [user@]host[:port]` is the whole UX for the common case.
- One local port serves HTTP proxy (plain HTTP + CONNECT for HTTPS) and SOCKS5.
- Survives network blips: detects dead connections and reconnects without
  asking for the password again.
- Errors are explained in plain words (wrong password, host unreachable,
  server forbids forwarding, host key changed).
- SSH-savvy users keep working: ssh-agent, default keys and common
  `~/.ssh/config` fields are honored, so `sshproxy myalias` works.

## Non-goals

- Advanced OpenSSH config: `ProxyCommand`, `Match`, `Include` semantics beyond
  what the parser library gives, Kerberos/GSSAPI, ControlMaster, certificates.
  Users who need these can run `ssh -D` themselves.
- Setting the OS system proxy, GUI/tray, serving PAC files.
- Built-in routing data (GeoIP databases, gfwlist/china-list), rule hot reload.
- Persisting passwords across runs (keychain).
- UDP / SOCKS5 UDP ASSOCIATE, SOCKS4, local proxy authentication.

## Anti-goals

- "My ssh works but sshproxy doesn't" for a plain host/user/password or
  host/key login. That case must always work.
- Silently accepting a *changed* host key.
- Exposing the proxy to the network by default.

## Constraints

- Go (latest), modern syntax. Source code and user-facing strings in English.
- KISS: few dependencies — `golang.org/x/crypto/ssh` (+ `agent`, `knownhosts`),
  `golang.org/x/term`, `github.com/kevinburke/ssh_config`.

## Approaches considered

- **A. Pure Go SSH client (chosen).** Single binary, works on Windows without
  OpenSSH, full control over password reuse on reconnect and error messages.
  Trade-off: only a subset of `~/.ssh/config` is supported.
- **B. Wrap the system `ssh -D`.** Inherits every OpenSSH feature, but needs
  the `ssh` binary, cannot reconnect without re-prompting for a password
  (short of `SSH_ASKPASS` hacks), and errors are only stderr text. Rejected
  because the target users are not SSH users.
- **C. Script around `ssh -D` + privoxy/gost.** Requires installing extra
  tools; not foolproof. Rejected.

## Design

### CLI

```
sshproxy [flags] [user@]host[:port]

  -l addr   local listen address (default 127.0.0.1:7890)
  -i file   private key file
  -J jump   jump host, [user@]host[:port] (same as ProxyJump)
  -rules f  routing rules file (default: everything goes through SSH)
```

- Missing destination: print usage with one example and exit 2.
- If `-l` is not given and 7890 is busy, try the next ports (up to +10) and
  print the one actually used. If `-l` is given explicitly and busy, fail.

### Resolving the destination

1. Parse `[user@]host[:port]`.
2. Look up `host` in `~/.ssh/config` (if present) for `HostName`, `User`,
   `Port`, `IdentityFile`, `ProxyJump`. Explicit CLI values win over config.
3. Defaults: user = current OS user, port = 22.
4. `ProxyJump` / `-J`: support a single hop (comma-separated chains are a
   non-goal for v1; reject with a clear message). The jump host is resolved
   with the same rules and authenticated the same way.

### Authentication

Offered in this order via `ssh.ClientConfig.Auth`:

1. ssh-agent (`SSH_AUTH_SOCK`), if available.
2. Public keys: `-i` file, else config `IdentityFile`s, else default
   `~/.ssh/id_ed25519`, `id_ecdsa`, `id_rsa` that exist. Encrypted keys prompt
   for the passphrase once.
3. Password, and keyboard-interactive (many servers only enable the latter;
   answer every prompt by asking the user, echo off unless the server says
   echo).

Every secret typed by the user is cached in memory for the lifetime of the
process and reused on reconnect, so a reconnect never prompts. If a cached
secret is rejected on reconnect, fall back to prompting.

Prompts go to the terminal (`golang.org/x/term`). Without a terminal and
without usable keys, fail with a message saying a key or agent is required.

### Host key verification

- Use `~/.ssh/known_hosts` via `knownhosts`.
- Unknown host: accept, append to `known_hosts` (create file/dir if needed),
  print the fingerprint (trust on first use, like `StrictHostKeyChecking
  accept-new`).
- Mismatch: refuse, explain that the server identity changed and how to
  remove the old entry if expected. Never auto-replace.

### The SSH connection manager

- Holds one `*ssh.Client` (via the jump host if configured).
- `Dial(ctx, network, addr)` opens a `direct-tcpip` channel on the current
  client. If there is no live client, it triggers/awaits a reconnect, bounded
  by the request context / a short timeout (~10s), then fails.
- Keepalive: every 15s send `keepalive@openssh.com` with a 10s timeout; on
  failure close the client so the next dial reconnects.
- Reconnect: one in flight at a time; exponential backoff 1s → 30s; log
  "Disconnected, reconnecting..." and "Reconnected".
- First connect: an unreachable server (e.g. network not up yet) is
  retried with the same backoff until Ctrl+C. Auth failures and host key
  mismatch are fatal (exit with a clear message), since retrying can't fix
  them. On reconnect every error is logged and retried with backoff; a
  rejected cached secret triggers a fresh prompt.

### Local proxy (single port)

A listener wrapper peeks the first byte of each accepted connection:

- `0x05` → SOCKS5 handler: no-auth method only, `CONNECT` command only,
  IPv4 / IPv6 / domain address types. Domain names are resolved on the remote
  side (pass hostname through to `direct-tcpip`).
- anything else → handed to an `http.Server`:
  - `CONNECT host:port` → hijack, dial through SSH, reply
    `200 Connection established`, pipe both directions.
  - absolute-URI requests (`GET http://...`) → forward with an
    `http.Transport` whose `DialContext` is the SSH dial; strip hop-by-hop
    and `Proxy-*` headers; stream the response back.
  - anything else (origin-form request, i.e. someone opened the proxy port
    in a browser) → `400` with a one-line explanation of how to use it.

All three paths (CONNECT, plain HTTP, SOCKS5) dial through one router
function `dial(ctx, addr)` that applies the routing rules below.

### Routing rules

PAC was considered and rejected: only browsers / system proxy settings read
PAC, while CLI tools (curl, git, go, docker, npm) do not. Routing inside
sshproxy works for every client, and users still configure a single proxy.

The router decides per destination: matched → dial through SSH, otherwise
→ dial directly from the local machine (`net.Dialer`, local DNS). Rules are
user-provided; nothing is bundled.

Rules file (`-rules file`), one rule per line, `#` comments, blank lines
ignored, **first match wins**:

```
# action  pattern
ssh     corp.example.com     # this domain and all subdomains
ssh     10.0.0.0/8           # CIDR, matches IP-literal targets only
direct  192.168.1.10         # exact IP
ssh     *                    # default for everything else
```

- Actions: `ssh`, `direct`.
- Patterns: domain (matches itself and subdomains, case-insensitive;
  `*.example.com` is accepted as the same thing), IP,
  CIDR, or `*`.
- No rule matched → `direct` (a rules file is a list of what to proxy).
  Without `-rules`, everything goes through SSH.
- Domains are never resolved locally just to match CIDR rules; CIDR/IP
  rules only match targets that are already IP literals. (Keeps DNS for
  SSH-routed hosts on the remote side.)
- Invalid lines fail startup with file:line and the reason.
- The startup banner shows the rules file and rule count when used.
- Direct-dial failures are reported like SSH dial failures, naming the
  route taken.

Dial errors are mapped to `502 Bad Gateway` (HTTP) or the matching SOCKS5
reply code; the body/log names the target and the reason (e.g. "server
refused to open connection to x:443: administratively prohibited — the SSH
server disables TCP forwarding (AllowTcpForwarding no)").

### Error messages (plain words)

| Situation | Message gist |
|-----------|--------------|
| TCP connect timeout / refused | can't reach host:port, check address/network |
| All auth methods rejected | wrong password or key not accepted by server |
| Host key mismatch | server identity changed, possible MITM, how to fix |
| `direct-tcpip` administratively prohibited | server forbids forwarding |
| Local port busy with explicit `-l` | port in use, pick another with `-l` |

### Output

Startup prints the banner shown in Intent (with the real port). Runtime logs
are one line per event (connect/disconnect/reconnect, failed dials). No
per-request logging by default.

### Layout

```
main.go        CLI parsing, wiring, banner, signal handling
config.go      destination resolution (+ ~/.ssh/config)
auth.go        auth methods, prompts, secret cache, host key callback
conn.go        connection manager: dial, keepalive, reconnect
proxy.go       listener sniffing, HTTP proxy, SOCKS5
rules.go       rules parsing and matching, router dial
*_test.go      tests
Makefile       build, test, release (cross-compile)
```

### Release

`make release` cross-compiles with `CGO_ENABLED=0` for
windows/darwin/linux × amd64/arm64 into `dist/` (`sshproxy-<os>-<arch>[.exe]`),
with `-trimpath -ldflags "-s -w"`. No CI and no code signing in v1:
unsigned binaries trigger a one-time SmartScreen / Gatekeeper warning,
documented in the README with how to allow it.

### Testing

- Integration tests run an in-process SSH server (`x/crypto/ssh` server with
  password auth and a `direct-tcpip` handler) plus an `httptest` origin
  server, then check through the proxy port: plain HTTP GET, HTTPS via
  CONNECT (TLS test server), SOCKS5 CONNECT.
- Reconnect test: kill the server-side connection, verify the next request
  succeeds without a prompt.
- Unit tests for destination parsing / config precedence and for
  forwarding-prohibited error mapping.
- Rules: parsing (valid/invalid lines), matching (subdomain, CIDR, first
  match wins, default), and an integration check that a `direct` target is
  reached without going through the SSH server.

## Decided by the user

- Pure Go implementation (approach A).
- Must be as foolproof as possible; users may not know SSH or have an ssh config.
- Routing is built into sshproxy (not PAC): matched destinations go through
  SSH, the rest are dialed directly from the local machine.

## Builder's calls (marked for review)

- Passwords kept in memory only, not persisted.
- No automatic system-proxy configuration; print instructions instead.
- Listen on `127.0.0.1` only by default; port 7890 with auto-increment.
- Trust-on-first-use host keys, written to `~/.ssh/known_hosts`.
- Single-hop `ProxyJump` only.
- Rules file format above (`ssh|direct <pattern>`, first match wins,
  unmatched → direct, no file → all SSH); CIDR rules don't trigger local DNS.
- Ship a cross-compile `make release`; no CI, no signing.
- Binary name `sshproxy`; Go module path `proxy-over-ssh` (no remote yet).
- Default user on Windows: strip the `DOMAIN\` prefix from the OS username.
- Set `HostKeyAlgorithms` from the algorithms already recorded in
  `known_hosts` for that host, so a known host is not misreported as a
  mismatch because the server offered a different key type first.
- Keyboard-interactive answers are cached per prompt text; one-time codes
  that get rejected on reconnect fall back to prompting.
